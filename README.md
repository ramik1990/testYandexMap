# Отзывы с Яндекс.Карт

Тестовое задание: подключаем карточку организации на Яндекс.Картах по ссылке, вытягиваем отзывы, рейтинг и счётчики, показываем постранично. Laravel 10 + Vue 3.

Что умеет:

- вход по логину/паролю (один пользователь из сида, Sanctum, cookie-сессия);
- страница настроек: вставил ссылку, нажал кнопку — организация сохраняется, парсинг уходит в очередь;
- страница организации: рейтинг, число оценок и число отзывов (это разные цифры, Яндекс их отдаёт отдельно), прогресс сбора, отзывы по 50 на страницу, история изменений между парсингами;
- парсер тянет все доступные отзывы (Яндекс отдаёт максимум 600), понимает, когда сломался, и не теряет собранное, если сломался на середине.

## Запуск

### Docker

```bash
cp .env.example .env
docker compose up -d --build
```

Открывать `http://localhost:8080` (порт — `APP_PORT`). Контейнер `app` на старте сам генерит `APP_KEY`, если он пустой, ждёт базу, накатывает миграции и сид. `queue` — тот же образ, но запускает `queue:work`. `.env` примонтирован внутрь, так что правки подхватываются после `docker compose restart`.

Логин: `admin@example.com` / `password` (меняется через `SEED_USER_EMAIL` / `SEED_USER_PASSWORD`).

Если сайт открывается не с `localhost:8080`, домен нужно добавить в `SANCTUM_STATEFUL_DOMAINS`, иначе API будет отдавать 401.

### Без Docker

Нужны PHP 8.1+ (pdo_mysql, mbstring, curl), Composer, Node 18+, MySQL 8.

```bash
composer install
npm install && npm run build
cp .env.example .env && php artisan key:generate
php artisan migrate --seed
php artisan serve
php artisan queue:work --tries=3 --timeout=600
```

Воркер обязателен: без него организация так и будет висеть «в очереди». На время отладки можно поставить `QUEUE_CONNECTION=sync`, тогда парсинг выполнится прямо в запросе (секунд 15), но в проде так делать нельзя, см. ниже.

Для отладки самого парсера есть команда, она не трогает базу и просто печатает сводку:

```bash
php artisan yandex:parse "https://yandex.ru/maps/org/yandeks/1124715036/"
```

### Переменные окружения

Кроме стандартных Laravel-переменных:

- `SANCTUM_STATEFUL_DOMAINS`, `SESSION_DOMAIN` — откуда SPA ходит в API;
- `SEED_USER_EMAIL`, `SEED_USER_PASSWORD` — пользователь из сида;
- `YANDEX_MAPS_HOST` — входной хост, по умолчанию `yandex.ru`. Яндекс всё равно редиректит на региональный домен по IP (у меня улетало на `yandex.kz`), парсер это отслеживает и дальше работает с тем хостом, куда попал;
- `YANDEX_MAX_REVIEWS` — потолок на организацию, 600;
- `YANDEX_REVIEWS_RANKING` — `by_time` (новые сверху) или `by_relevance_org`, как на сайте по умолчанию;
- `YANDEX_HTTP_TIMEOUT`, `YANDEX_DELAY_MIN_MS`, `YANDEX_DELAY_MAX_MS` — таймаут запроса и случайная пауза между запросами;
- `YANDEX_PROXY` — прокси в формате Guzzle, `http://user:pass@host:port`;
- `YANDEX_USER_AGENTS` — свой список UA через `|`, если пусто — берётся встроенный.

## Как устроено

Вся работа с Яндексом лежит в `app/Services/YandexMaps`, контроллеры про Яндекс ничего не знают.

- `UrlResolver` — достаёт `businessId` из ссылки. Форматов оказалось больше, чем я думал: `/maps/org/<slug>/<id>/`, `/maps/org/<id>`, `?oid=<id>` из ссылок с карты, `/profile/<id>/`, `maps.yandex.ru`, региональные домены, короткие `/maps/-/XXXX` (их раскрываю по редиректу).
- `YandexHttpClient` — обёртка над Guzzle: cookie-сессия, случайный User-Agent, прокси, паузы, определение капчи/бана.
- `PageExtractor` — из HTML карточки достаёт рейтинг, счётчики, название, адрес и токены для API.
- `RequestSigner` — считает подпись `s` для внутренних запросов (про неё ниже).
- `ReviewsFeed` — ходит в `fetchReviews` постранично, обновляет csrf при необходимости.
- `YandexMapsParser` — связывает всё вместе и отдаёт `ParseResult`.
- `Exceptions/` — типизированные ошибки с кодом и флагом «можно ли повторять».

Дальше обычный Laravel: `OrganizationService` (подключение, запуск парсинга), `ReviewSyncService` (upsert отзывов и снимок), `ParseOrganizationJob`, тонкие контроллеры с FormRequest/Resource/Policy.

Фронт в `resources/js`: три страницы (`LoginPage`, `SettingsPage`, `OrganizationPage`), компоненты, композаблы `useAuth`, `useAsync` (единый loading/error для всех запросов, чтобы не копипастить try/catch) и `usePolling`.

База:

- `organizations` — карточки: `yandex_id`, `source_url`, `title`, `address`, `rating`, `rating_count`, `review_count`, `last_parsed_at`. Уникальность по `(user_id, yandex_id)`.
- `reviews` — `external_id` (id отзыва у Яндекса), автор, аватар, «Знаток города N уровня», оценка, текст, дата, лайки/дизлайки, ответ организации, `content_hash`, `last_seen_at`. Уникальность по `(organization_id, external_id)`.
- `parse_runs` — запуски: статус, `pages_done/pages_total`, `reviews_fetched`, `attempts`, код и текст ошибки.
- `organization_snapshots` — снимок после каждого успешного запуска, чтобы видеть, что поменялось.
- плюс `jobs`, `sessions`, `users`, `failed_jobs`.

## Парсинг

Это основная часть, поэтому подробно.

Открыл карточку с вкладкой Network и покрутил список отзывов. При прокрутке фронт Яндекса дёргает

```
GET /maps/api/business/fetchReviews?ajax=1&businessId=…&csrfToken=…&locale=ru_RU&page=2&pageSize=50&ranking=by_relevance_org&reqId=…&s=2891569646&sessionId=…
```

и получает чистый JSON: `data.reviews[]` с id, автором, оценкой, текстом, ISO-датой, реакциями и ответом организации, плюс `data.params.count` — общее число отзывов. То есть DOM парсить вообще не нужно.

Откуда брать параметры. Страница `https://yandex.ru/maps/org/<id>/reviews/` содержит `<script class="state-view">` с большим JSON. В `config` лежат `csrfToken` и `requestId`, `sessionId` спрятан в `config.counters.analytics`. Там же, в `stack[].results.items[]`, сама организация: `title`, `fullAddress` и `ratingData` с `ratingValue`, `ratingCount`, `reviewCount` — это и есть средний рейтинг, количество оценок и количество отзывов. На всякий случай есть запасной вариант — микроразметка schema.org (`<meta itemProp="ratingValue">` и т.д.), она тоже присутствует на странице.

Подпись `s`. Без неё сервер отвечает 400, и это было самое интересное. Перебрал стандартные хеши против перехваченного значения: подошёл DJB2 в варианте с xor (`h = h * 33 ^ c`, старт 5381, uint32) от закодированной query-строки без самого `s`. В `RequestSignerTest` этот перехваченный запрос лежит как эталон, если Яндекс поменяет алгоритм — тест покраснеет первым.

Ещё пара нюансов, на которые наступил:

- csrfToken привязан к cookie-сессии. Запрос без cookie или с чужим токеном возвращает 200 и тело `{"csrfToken": "новый"}` вместо данных. Парсер один раз подставляет новый токен и повторяет; если получает такой ответ второй раз — считает, что схема изменилась, и останавливается.
- Яндекс отдаёт не больше 600 отзывов: 12 страниц по 50, а на 13-ю приходит `{"error":{"code":500}}`. Число страниц считаю как `min(count, YANDEX_MAX_REVIEWS) / 50`, а ошибку после первой страницы трактую как конец списка, а не как падение.
- Хост важен: страница с `yandex.ru` уходит на `yandex.kz`, и токены действуют только там.

На организацию с 600 отзывами выходит 13 запросов, с паузами около 15 секунд.

### Почему внутренний API, а не headless-браузер

Я делал через JSON-запросы. Сравнивал так:

Скорость и ресурсы. 13 лёгких запросов против загрузки карты, тайлов, бандлов и ручной прокрутки виртуализированного списка. Один PHP-воркер спокойно обходит сотни карточек в час, Chrome на каждую тратит минуты и сотни мегабайт.

Качество данных. В JSON есть id отзыва, нормальная дата, точные счётчики, ответ организации. В DOM — «12 июля» без года, текст, обрезанный кнопкой «ещё», и список, из которого элементы выгружаются при прокрутке.

Хрупкость. Headless ломается при каждом переименовании CSS-классов, а Яндекс их меняет регулярно. JSON-подход не зависит от вёрстки, но зависит от контракта внутреннего API и от подписи `s`. Это главный риск: если алгоритм поменяют, всё встанет. Зато встанет громко и сразу (400 или пустые данные), а чинится точечно в одном классе.

Анти-бот. У Яндекса SmartCaptcha, и она headless-браузеры тоже отлично детектит по fingerprint, так что прокси нужны в любом случае. Обычный HTTP-клиент с cookie и человеческими заголовками выглядит как обычный пользователь.

Эксплуатация. Чистый PHP внутри queue-воркера, никакого Chrome в контейнере.

Если Яндекс перенесёт подпись на что-то невоспроизводимое (например, привяжет к browser fingerprint), headless останется запасным планом: заменить `YandexHttpClient` и `ReviewsFeed`, остальное не трогать.

## Дополнительные требования

### 1. Устойчивость к смене разметки

Принцип простой: парсер никогда не возвращает пустоту молча. На каждом шаге проверяется, что в ответе есть то, что обязано быть, а нарушение превращается в исключение с кодом:

- `invalid_url` — не Яндекс.Карты или в ссылке нет id. Не ретраится.
- `source_unavailable` — таймаут, 5xx, 404 карточки, ошибка API на первой странице. Ретраится.
- `blocked` — 403/429, редирект на `showcaptcha`, маркеры SmartCaptcha в HTML. Ретраится с бэкоффом.
- `markup_changed` — нет `state-view`, JSON не декодируется, нет `csrfToken`/`sessionId`, в state нет организации и микроразметки тоже нет, API вернул не JSON, нет `data.reviews` или `data.params.count`, ни один отзыв на странице не разобрался, повторное требование csrf. Не ретраится, смысла молотить нет.
- `reviews_skipped` — не ошибка, а предупреждение: часть отзывов пропущена, остальное собрано и сохранено.
- `empty_response` — первая страница пустая, хотя карточка говорит, что отзывы есть. Ретраится.

Как парсер понимает, что сломался: сверяет выдачу API с `reviewCount` из карточки (пустая выдача при ненулевом счётчике — ошибка, а не «нет отзывов»), в контекст ошибки кладёт ключи, которые пришли вместо ожидаемых, пишет всё в отдельный `storage/logs/parser.log`, сохраняет `error_code`/`error_message` в `parse_runs` и показывает их в интерфейсе. На проде на `markup_changed` вешается алерт. Контракт закреплён фикстурами в `PageExtractorTest`: при смене разметки первым делом обновляется фикстура.

Деградация вместо падения. Отдельный отзыв с неожиданной структурой (нет `rating`, нечитаемая дата) пропускается и уходит в лог вместе со своими ключами — из-за одной аномалии на пятой странице не теряются одиннадцать остальных. Исключение бросается, только если не разобралась вся страница целиком: это уже смена контракта, а не единичный случай. Если сбор всё-таки прервался на середине, уже полученные отзывы плюс рейтинг и счётчики из карточки сохраняются, запуск получает статус `partial`, а в интерфейсе появляется жёлтая плашка «Собрано частично» с причиной вместо красной ошибки и пустой карточки. Ретраиемые ошибки (`blocked`, `source_unavailable`) по-прежнему уходят в повтор целиком — там есть смысл перезапустить сбор с первой страницы. В снимке истории у частичного сбора не считается `missing`, чтобы недособранные страницы не выглядели как удалённые отзывы.

### 3. Масштаб и фоновая обработка

Парсинг в HTTP-запросе не выполняется никогда. `POST /api/organizations` сохраняет организацию, создаёт `parse_runs` со статусом `pending` и ставит `ParseOrganizationJob` в очередь. Драйвер `database`, чтобы не тащить Redis в тестовое, в проде очевидно Redis + Horizon.

Job после каждой страницы обновляет прогресс (`pages_done/pages_total/reviews_fetched`) и сразу пишет отзывы этой страницы в базу — фронт опрашивает `GET /api/organizations/{id}` раз в 2,5 секунды и показывает прогресс-бар и уже полученные отзывы. Три попытки с бэкоффом 30/120/300 секунд, ретраятся только временные ошибки. Job уникальный по `organization_id`, плюс `OrganizationService` не создаёт новый запуск, пока есть активный — повторные нажатия «Обновить» ничего не плодят. Таймаут job 600 секунд.

Прикидка на 50 филиалов по 600 отзывов: 650 запросов, с паузой около секунды и 2–3 воркерами это 5–10 минут, спокойно укладывается в ночное окно. Регулярность — `schedule`, раз в сутки job на каждую организацию с разбросом по времени; при росте — отдельные очереди и `RateLimited` middleware на job, чтобы общий поток в Яндекс был ограничен глобально, а не только паузами внутри одного job.

### 4. Анти-бан

Что есть сейчас: случайные паузы между запросами, ротация User-Agent на каждую сессию парсинга, реальные Accept/Accept-Language, полноценная cookie-сессия (сначала страница, потом API с её cookie — так делает обычный браузер), прокси через `YANDEX_PROXY`, обнаружение бана и бэкофф.

Что нужно для регулярного обхода многих карточек:

- глобальный лимитер на очередь в Redis (условно 30 запросов в минуту на IP), а не только паузы внутри job;
- пул резидентных/мобильных прокси с привязкой сессии к прокси: страница и все её `fetchReviews` через один IP; плохие прокси временно выводятся;
- размазывать обход по суткам в случайном порядке, а не «все филиалы в три ночи»;
- инкрементальность: с сортировкой `by_time` можно остановиться, как только страница целиком состоит из известных отзывов с тем же `content_hash`, — обычно это 1–2 запроса вместо 13;
- «нас забанили»: job освобождается с бэкоффом, прокси помечается, растёт счётчик; при серии банов — circuit breaker на весь обход на N минут и алерт; в интерфейсе статус «источник временно недоступен», данные остаются прошлые;
- метрики по кодам ошибок и капчам: их рост — первый признак, что антибот поменялся.

### 5. Идемпотентность и история

Отзыв идентифицируется `external_id`, `updateOrCreate` по `(organization_id, external_id)` обновляет запись вместо дубля. Организация — по `(user_id, yandex_id)`, одна и та же ссылка второй раз не создаёт вторую карточку. Это проверено: второй прогон по той же организации даёт «+0 новых, 0 изменённых».

У отзыва хранятся `content_hash` (оценка, текст, дата, реакции, ответ организации) и `last_seen_at`. За один проход считается: `added` (новый id), `updated` (id известен, хеш другой), `unchanged`, `missing` (были в базе, но в этом обходе не встретились — удалены модерацией или вылетели за окно 600). После каждого успешного запуска создаётся `organization_snapshots` с рейтингом, счётчиками, числом отзывов в базе и JSON `changes`, куда входит и блок `before` со старыми значениями. В интерфейсе это «История изменений».

Что бы расширил: `review_versions` с полной копией отзыва при смене хеша (посмотреть, как правили текст или оценку), `deleted_at` у отзывов, которые не приходят N обходов подряд, и хранение сырого JSON ответа, чтобы перепарсить задним числом, если модель данных поменяется.

## Пагинация и что кэшировать

Результат парсинга живёт в базе, страницы отдаются обычной серверной пагинацией `GET /api/organizations/{id}/reviews?page=N` по 50 штук с индексом по `(organization_id, published_at)`. Тянуть 600 отзывов с Яндекса на каждый просмотр — это 15 секунд ожидания и прямой путь к бану, а данные при этом меняются редко. Обновление либо явное (кнопка), либо по расписанию.

## API

Sanctum SPA: перед мутирующими запросами фронт дёргает `GET /sanctum/csrf-cookie`.

- `POST /login`, `POST /logout`
- `GET /api/user`
- `GET /api/organizations` — список с последним запуском
- `POST /api/organizations` `{url}` — подключить, `201` новая, `200` уже была
- `GET /api/organizations/{id}` — организация, рейтинг, счётчики, прогресс
- `PUT /api/organizations/{id}` — перепарсить
- `DELETE /api/organizations/{id}`
- `GET /api/organizations/{id}/reviews?page=N`
- `GET /api/organizations/{id}/snapshots`

422 — валидация (`errors.url`), 403 — чужая организация, 503 с `code` — ошибка парсера, если она случилась синхронно.
